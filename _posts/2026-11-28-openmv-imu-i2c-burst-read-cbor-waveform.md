上个月做的那台 OpenMV 循迹小车，最近加了云台，需要实时知道车身的俯仰和横滚，用来做前馈补偿。板载 IMU 六轴数据我一开始读得很随意：陀螺三轴读三次，加速度三轴再读三次，凑成一帧送进姿态解算。小车慢速跑的时候没问题，一旦过减速带或者云台快速转，算出来的角度就开始抖，抖的方向还没有规律。

我起初怀疑是滤波参数不行，换了几组都没有改善。把原始数据打到表格里逐行看才发现问题：同一帧里，陀螺的 Z 轴和加速度的 X 轴之间总是差着一点相位。也就是说，我拼出来的"一帧"根本不是同一个时刻的六个数。这篇就把这个坑和后面的调试方式一起讲清楚。

## 一、六个数为什么不是同一时刻的

先看 I2C 一次读寄存器到底发生了什么。`readfrom_mem(addr, reg, n)` 展开后是一次完整事务：START、从机地址加写位、一个字节的寄存器地址、重复 START、从机地址加读位、n 个字节数据、STOP。也就是说，每调一次，总线上就走一趟完整的往返。

传感器不是静止的。它按自己的输出数据率（ODR）源源不断地更新寄存器，我这边读第 1 个轴和读第 6 个轴之间隔着五趟完整事务，中间完全可能跨过一次更新。振动越剧烈、ODR 越高，这种错位的概率越大。姿态解算对时间对齐很敏感：加速度用来定重力方向、陀螺用来积分角速度，两者差半个采样周期，融合出来的角度就会来回摆。

错位窗口有多大，可以粗算。400 kHz 下，一次读两个字节的事务包含起始位、两段地址、寄存器地址和停止位，按位时间累加大约 0.12 ms，六次就是 0.7 ms 上下。如果传感器配成 200 Hz，一帧周期只有 5 ms，这个窗口就占到了七分之一；云台快速转动时角速度本身在变，这七分之一里积出来的误差自然显眼。采样率再往上提，比例还会更难看。

关键在于 I2C 协议本身给了解决办法：读事务里，从机每送出一个字节就把内部寄存器地址加一。所以只要在**同一次**事务里连读 12 个字节，拿到的就是连续的 12 个寄存器，从机不会在事务中间把总线让出去。这个"自增"是 I2C 读写时序的一部分，LSM6DS 系列、MPU6050 这类常见惯性传感器都支持，不需要额外的驱动配合。

一句话概括差别：逐寄存器读，是六次独立的对话；突发读，是一句话把六个答案一起要到。

## 二、把六次事务压成一次

以 LSM6DS 系列为例，0x28 起是陀螺三轴，紧跟加速度三轴，每个轴占两个字节、小端序。一次读 12 字节就够：

```python
from machine import I2C
import struct

i2c = I2C(1, freq=400_000)   # 总线号按板子来，OpenMV 上先 i2c.scan() 确认
ADDR = 0x6A                   # 传感器 SA0 接低电平时的 7 位地址

def read_six_axis(addr=ADDR, reg=0x28):
    raw = i2c.readfrom_mem(addr, reg, 12)      # 一次事务，12 字节
    gx, gy, gz, ax, ay, az = struct.unpack("<6h", raw)
    return ax, ay, az, gx, gy, gz

ax, ay, az, gx, gy, gz = read_six_axis()
```

对比一下原来的写法，问题一目了然：

```python
# 反例：六次独立事务，中间可能被新样本插队
def read_six_axis_slow(addr=ADDR):
    def rd(reg):
        return int.from_bytes(i2c.readfrom_mem(addr, reg, 2), "little", signed=True)
    gx = rd(0x28); gy = rd(0x2A); gz = rd(0x2C)
    ax = rd(0x2E); ay = rd(0x30); az = rd(0x32)
    return ax, ay, az, gx, gy, gz
```

MPU6050 的寄存器排布不太一样：加速度从 0x3B 开始，温度夹在中间，陀螺在 0x43。想一次读完就连读 14 个字节，再按偏移量切片，原理相同。

| 维度 | 逐寄存器读 | 突发读 |
|---|---|---|
| I2C 事务次数 | 6 | 1 |
| START/STOP 次数 | 各 6 次 | 各 1 次 |
| 一帧六轴的时刻 | 可能跨 1 次以上传感器更新 | 落在同一事务内 |
| 400 kHz 下的数据阶段 | 6 段开销叠加 | 12 字节，不到半毫秒 |
| 出错时的粒度 | 单轴失败，帧不完整 | 整帧失败，直接丢弃重读 |

这里有一点必须说清楚，免得把突发读当万能药：它只保证同一次总线事务内读到的是连续寄存器，不保证事务开始前传感器刚好更新完。要真正做到"一帧就是一个采样点"，还得看状态寄存器里的新数据标志，或者用传感器自带的 FIFO。突发读解决的是"别让总线把一帧拆散"，数据就绪与否是另一层问题。我在小车上加了一步：读完之后检查 DATA_READY 位，没置位就沿用上一帧，偏差立刻小了一个量级。

顺带记一个硬件侧的注意点：OpenMV 板载 IMU 往往和其它 I2C 器件挂在同一条总线上。突发读把事务数从六次压到一次，客观上缩短了占用总线的时间，也降低了被其它器件插队的机会；但前提是上拉电阻撑得起当前速率。400 kHz 下波形上升沿不够陡，读出来的数据会随机出错，而且报错位置不固定，很容易误判成传感器坏了。遇到这种情况先把速率降到 100 kHz 复现，能稳定就说明是总线电气问题，而不是代码问题。

## 三、把波形送进 IDE，而不是 print

六轴对齐之后，下一个问题是看数据。用 `print` 打 CSV 到串口终端，采样率一上去就开始丢行，而且打印本身要时间，等于给采集循环加了一段不确定的延迟。OpenMV 5.0.1 的协议通道里新增了 `waveform` 控件，配合原有控件可以在 IDE 里直接看曲线。

按 v5.0.1 的说明，`protocol.CBORChannel.add()` 支持 `text`、`lineedit`、`pushbutton`、`spinbox`、`radio`、`waveform` 六种控件，其中 `waveform` 是一维时间序列，带 `sample_rate`、`series` 和 `typecode` 参数，把交错的采样字节赋值进去就会流式发送到 IDE。骨架大致是这样：

```python
import protocol

ch = protocol.CBORChannel()
ch.add("waveform", "accel", sample_rate=200, series=("x", "y", "z"), typecode="h")

while True:
    ax, ay, az, _, _, _ = read_six_axis()
    # 交错排列的三轴采样，按 typecode 的字节宽打包
    ch["accel"] = struct.pack("<3h", ax, ay, az)
```

具体参数以本机 IDE 与固件版本为准，我第一次接的时候也是对着示例脚本改的。但思路值得记住：走的是同一条 USB 链路，可它是二进制通道，IDE 负责解析和绘图，不占标准输出，也不会因为终端滚屏把主循环拖慢。`print` 适合看离散事件和报错，连续波形交给控件更合适。

需要提醒的是，波形控件同样受 USB 带宽约束。六轴按 200 Hz 全量发是够的，如果后面要上 1 kHz 的振动分析，就得在板子上先算包络或者降采样，只发特征量。这一点和我在风机监测板上做本地频谱是同一个取舍：原始数据留在采集端，往上发的是结论。

另外，5.0.1 还让 `protocol.poll()` 回归了，用于自己实现传输层时手动驱动一次协议任务。我现在还用不到，但如果以后把 OpenMV 的数据改走 UART 或 LoRa 转发，这个入口就是手边现成的。

## 四、v5.0.1 里两个影响调试的行为变化

这次升级固件，顺手把更新日志读完了，有两个变化值得单独记一笔。

第一个是帧缓冲里的图像不再立即刷到 IDE。以前用 `copy_to_fb=True` 加载一张图，它会马上被推送到预览，导致你在返回的图像上画的标注永远看不到。现在行为统一了：图像先标记为待刷出，等下一张图覆盖帧缓冲之前，连同标注一起发出去。好处是标注终于能看见，代价是"只加载一张图就结束"的脚本必须自己刷一次：

```python
img = image.Image("example.bmp", copy_to_fb=True)
img.flush()          # 新增：立刻送到 IDE 预览
time.sleep_ms(1000)
```

第二个是 `import sensor` 现在会打印弃用警告。V5 把 `sensor` 变成了构建在 `csi` 之上的 Python 兼容层，`get_fb()`、`alloc_extra_fb()` 这类在 `csi` 里没有对应物的函数会直接抛 `OSError`。新脚本尽早迁到 `csi`，别等到某天固件把这个兼容层删掉再回头改。

还有一个和硬件采集直接相关的修复：JPEG 编码器原来有 1 MB 的输出上限，现在按可用内存来定，溢出也会被正确报告，而不是悄悄写出一张缺了结束标记的半截图。之前用高分辨率、高质量拍图偶尔下半张空白，就是这么来的。拍完检查一下文件末尾有没有结束标记，仍然是我保留的习惯。

## 小结

六轴数据"差一拍"，根因不在滤波，而在六次独立的 I2C 事务；改成一次突发读，再配合数据就绪位，一帧才是真正的一帧。调试上，连续波形走 CBOR 波形控件，离散事件走 `print`，各管各的。固件升级后记得读一遍行为变更，`flush()` 和 `sensor` 弃用这两条，都是升级当天就会碰到的。
